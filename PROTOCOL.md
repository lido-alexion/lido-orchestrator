# Protocol and durable reconciliation

For every supervisor execution, follow [SUPERVISOR_PROTOCOL.md](SUPERVISOR_PROTOCOL.md). [QUICK_GUIDE.md](QUICK_GUIDE.md) contains prompts only; prompts do not invoke CLI operations.

SQLite is the authority for task, event, supervisor registration, route, and dispatch state. The manual `reconcile` command, periodic `serve` loop, and any local native trigger must call the same `Engine.reconcile()` entry point against the same database. `BEGIN IMMEDIATE`, unique task/intent/event keys, leases, and attempt fencing serialize claims across processes. A crash before dispatch handoff leaves a recoverable pending intent with a stable idempotency key. A crash after durable `dispatching` state is ambiguous and moves to review; it is never automatically replayed. Stale worker callbacks cannot alter a newer attempt.

Supervisor enrollment is trusted-local only. A registration binds a supervisor ID to a project ID and operator-selected worker association label. The one-time route token is held by the operator; SQLite stores its digest. A route signature is HMAC-SHA256 over UTF-8 lines `supervisor_id`, `event_id`, authoritative `event_type`, and integer Unix issue time. The receipt is valid for a five-minute clock window, is checked against the registered project's authoritative event/task/outbox rows, and can be consumed once per supervisor/event pair. It returns SQLite event data, never caller-supplied content. Unregistering revokes future routes. Routing grants no approval or execution authority. Lease age is checked in every authorization path, independent of reaper timing. `reconcile` reaps leases but never renews them; only an explicit authenticated supervisor execution can renew a lease. Trusted-local actor labels are audit context, not chat identity. Scoped tasks bind to one registration generation; takeover fences old-generation tasks and preserves pending approvals. Never-dispatched pending work may be explicitly adopted per task into an active same-project generation, always returning to required approval. A deboarded ID stays revoked and may be replaced by a new registration. Pending never-dispatched dependency trees can be explicitly disposed; attempted or ambiguous tasks cannot be adopted, disposed, or replayed. Takeover does not re-enable disabled recipients. Worker callbacks are trusted in-process events; there is no generic CLI event injection or authenticated callback endpoint.

The SMTP adapter claims one supervisor-notifiable event at a time only when its exact configured recipient is enabled for the event task's active supervisor generation. It excludes unscoped tasks and other supervisors' events. A pre-send check repeats the lifecycle, generation, recipient, and event-type check. A per-event outbox lease covers the configured throttle wait and SMTP exchange; a database-wide send slot serializes concurrent SMTP processes. Its lease is bounded to at least 60 seconds and is calculated as `min(5000, max(60, int(timeout * 8 + min_interval + 10)))`, covering up to eight connection operations at the configured timeout plus the maximum 3600-second interval. Expired claims/slots recover after process death. A send that succeeds remotely but loses its local acknowledgement can be retried and produce a duplicate; stable Message-ID supports downstream deduplication but does not promise exactly-once email. Retry delay is capped exponential backoff. SMTP refusal, timeout, TLS, or auth errors fail closed into retry; no error exposes credential or server detail. A lifecycle change cannot recall a send already in progress.

No native mail or chat reader is shipped. Manual reconciliation, periodic reconciliation, and any future event-specific wake must converge on the same SQLite authority and authorization path. An event wake only requests inspection; it never approves or dispatches. A provider adapter must verify authenticated identity, exact task owner/generation, recipient binding, replay limits, and event authority. See the provider-specific discovery and test gates in [SUPERVISOR_PROTOCOL.md](SUPERVISOR_PROTOCOL.md). OpenAI's current task documentation describes Gmail sender/subject filters and Slack channel-message triggers requiring an `@ChatGPT` mention; these behaviors are not integrated or target-account-verified here. It also documents that deleting a chat pauses a task but does not delete its shared task link, deleting a task does not delete its associated chat, and pause/delete should not be relied upon to stop an already-running execution. Filters only select candidates and never establish identity or authority. Same-chat routing, multiple subscriptions, account eligibility, and deletion behavior must be verified in the target account before a provider adapter is enabled.
